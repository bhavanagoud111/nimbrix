# ADR-0002: PostgreSQL 16 as the single system of record

- Status: Accepted
- Date: 2026-10-10

## Context

Data includes relational entities (tenants, users, approvals), append-only audit
events, time-series cost line items (90+ days × accounts × services × resources), and
job state. The demo must run offline on a laptop.

## Decision

Use **PostgreSQL 16** for everything: OLTP entities, cost line items, job queue, and
audit log. Access via **SQLAlchemy 2** (psycopg 3 driver) with **Alembic** migrations.

Conventions:

- UUID primary keys generated by `gen_random_uuid()` (built in since PG 13).
- `timestamptz` for every timestamp; application treats all times as UTC.
- Money as `NUMERIC` (Python `Decimal`) with an explicit ISO 4217 currency column; never floats.
- Deterministic constraint names via a SQLAlchemy naming convention (see `db/base.py`).
- Every tenant-owned table carries `tenant_id` and indexes that start with it.
- `statement_timeout` set per connection (default 5 s for API sessions).
- Audit events are append-only; the application role will lack UPDATE/DELETE on them (Phase 1/8).

## Alternatives considered

- **TimescaleDB / ClickHouse for cost data** — better at very large volumes, but adds an
  extension or second store. Demo-scale data (≈10⁵–10⁶ rows) is well within plain
  PostgreSQL with proper indexes and, if needed, monthly partitioning. Revisit with
  Phase 9 benchmarks.
- **SQLite for local demo** — diverges from production behavior (types, locking, `SKIP LOCKED`). Rejected.

## Consequences

- One backup/restore story. Integration tests run against a real PostgreSQL 16, never SQLite.
- Migration correctness is tested: upgrade from empty, downgrade to base, and
  `alembic check` (no drift between models and migrations) run in CI.
